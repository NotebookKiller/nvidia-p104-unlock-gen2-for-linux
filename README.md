## Why the unlock is needed

The P104's vBIOS declares the PCIe capability as Gen1, so the driver initializes the link at 2.5GT/s.
Worse: **the driver actively downgrades the link back to Gen1 on every `cuInit`**.

Static analysis located the path (`_nv017105rm` is the driver's own `set_link_speed(mode)`):

```
rm_init_adapter+0xcd          <- every cuInit goes through here
  -> _nv017755rm+0x98          <- if (mode == current speed) return;
    -> _nv017105rm(mode=1)     <- mode 1/2/3 = Gen1/Gen2/Gen3
        mode=1 -> or $0x80000 -> write 0x8C040.SPEED=2 -> link 2.5GT/s
```

So there are two routes:
- **heal afterwards** (the old approach): detect the drop, then push the link back — recovery takes 3.8 s, and bandwidth is halved meanwhile
- **never downgrade** (this approach): intercept that `mode=1` at function entry — the link stays at Gen2 permanently

---

## What the solution consists of

Two parts, both required:

### ① The 2-byte patch (the core)

Narrow the mode whitelist at `_nv017105rm`'s entry from `{1,2,3}` to `{2,3}`:

```asm
- 127d66: 8d 42 ff     lea  -0x1(%rdx),%eax    ; eax = mode - 1
- 127d81: 83 f8 02     cmp  $0x2,%eax
+ 127d66: 8d 42 fe     lea  -0x2(%rdx),%eax    ; eax = mode - 2
+ 127d81: 83 f8 01     cmp  $0x1,%eax
  127d84: 0f 87 ...    ja   1280c8             ; this one stays untouched
```

The new predicate `(mode-2) > 1` (unsigned):

| mode | mode-2 | >1? | result |
|---|---|---|---|
| 1 | `0xFFFFFFFF` (underflow) | yes | **bail** <- the only behavioral change |
| 2 | 0 | no | continue -> Gen2 |
| 3 | 1 | no | continue -> Gen3 |
| ≥4 | ≥2 | yes | bail (**exactly equivalent to the original logic**) |

The bail jumps to `1280c8`, the function's only return point, which returns `%r12d` —
zeroed by `xor` at entry, so it returns **0 = CUDA_SUCCESS**. The driver believes the set succeeded; no error, no retry.

**Only 2 bytes change; every other instruction, every other branch, every other mode stays untouched.**

### ② The gen2kr kernel module (only handles the first push)

The patch only stops the driver from downgrading; the link still has to be raised first. That needs:
- unlocking the endpoint's declaration (`0x8841C` etc.), so `LINK_CAP2` goes from `0x02` to `0x06`
- writing `0x8C040.SPEED=1` (5.0GT/s)
- TLS=2 in `LNKCTL2` on both ends, retrain from the root port

**Timing is critical**: it must happen the instant `nv_pci_probe` returns; any later and RM has already finished its internal init at Gen1,
and touching the link afterwards only yields "link at Gen2 but bandwidth still Gen1" (the internal datapath stays configured for Gen1).

`gen2kr.ko` attaches a `kretprobe` on `nv_pci_probe` and pushes at exactly that moment.

It also carries a guard (polls `LNKSTA` every 200 ms), but **with the patch in place the guard should be a no-op** —
the guard is just a safety net (the patch is lost on driver upgrades; then the guard can pull the link back).

### One bug fixed during reproduction
`20-install.sh` originally used the combination "`CAP2=0x0002` + `TLS=1` + Gen1" to detect a "driver-side locked state",
but that **is exactly what a healthy factory-locked machine looks like** — on a clean machine after a reboot it would false-positive every time.

It was changed to detect the real lock-up signature with `is_stuck()` (in `bin/_common.sh`) —
**the unlock bits were written but did not latch**:

```
0x8841C bit15|bit13|bit11 are set (= unlock was written; factory 0xc0b40500 -> & 0xA800 == 0)
but CAP2 is still 0x0002 (= did not latch)
and the link is still Gen1
```

## ⚠ After a reboot the link returns to Gen1

| item | after reboot |
|---|---|
| The 2-byte patch (inside `nvidia.ko`) | **kept** |
| `gen2kr` (manual insmod, no service) | **lost** |

The patch is only responsible for "no more downgrading", not for "raising the link". At power-on the endpoint declares Gen1
(`LCAP2=0x02`); with nobody unlocking and nobody pushing, the link stays at 2.5GT/s.

### When is an nvidia reload actually needed

| scenario | reload? |
|---|---|
| Just ran `patch_no_gen1.py apply` (the .ko changed) | **yes** — otherwise the kernel still runs the old code |
| After a reboot (the patch is already in the .ko) | **no** — `push.sh` is enough |
| Re-applying after the patch was lost | **yes** |

`bin/20-install.sh` decides automatically (comparing md5 before/after apply):
- the .ko changed -> `✓ patch was freshly written => a reload of nvidia is required for it to take effect`
- the .ko unchanged -> `✓ patch was already in place (.ko unchanged) => no reload needed`

Or force it: `sudo bash bin/20-install.sh --no-reload`

### Three automation options (by intrusiveness)

| option | how | intrusiveness |

## Manual reproduction (no scripts, one command at a time)

Below is the minimal reproducible sequence. Assumptions:
- you are in the **repo root** (the cloned directory); relative paths are used below
- device `0000:01:00.0`
- driver at `/lib/modules/$(uname -r)/updates/dkms/nvidia.ko` (if your driver lives elsewhere, see `KO` in `bin/_common.sh`)

### Step 0 — build the probes and the module

> ★ The kernel module must be built on **the machine that runs the P104** (with the kernel headers matching `uname -r`).
> ★ Do not use `sudo` — NFS root_squash makes make fail with `.gen2kr.o.d: permission denied`.

```bash
mkdir -p build

# zero-DMA context probe (only creates/destroys CUDA contexts, to watch for triggered downgrades)
gcc -O2 -o build/minictx src/minictx.c -ldl

# bandwidth test (★ must be 512MB×15; short tests hit pitfalls, see "measurement traps" below)
gcc -O2 -o build/bwtest2 src/bwtest2.c -ldl

# kernel module (★ normal user, no sudo)
cd drivers/580.178.04/kernel/6.12.113
make -C /lib/modules/$(uname -r)/build M=$PWD modules
cp gen2kr.ko ../../../../build/
cd ../../../../    # back at the repo root; every later command runs here
```

Or just run `bash bin/build.sh` once to do all three of the above.

### Step 1 — confirm the starting state

```bash
# is the device there
lspci -Dn | grep 10de:1b87

# look at the link ("Speed 2.5GT/s" = currently Gen1, needs the unlock)
lspci -vv -s 01:00.0 | grep -o 'LnkSta:.*'

# look at the registers (the only trustworthy indicator)
sudo python3 bin/peek-regs.py
```

Expected output (locked):
```
0x88084 = 0x00453c41   LNKCAP  MaxSpeed=1
0x880a4 = 0x00000002   LNKCAP2 = 0x02  (declares Gen1 only)
0x88088 = 0x10410140   LNKSTA  CurSpeed=1
0x8c040 = 0x20585800   SPEED=2 (2.5GT/s)
```

### Step 2 — apply the patch

```bash
# first check the patch can be located uniquely (prints the signature hit counts and the bytes to change)
sudo python3 bin/patch_no_gen1.py check

# apply (backs up to nvidia.ko.orig_nogen1 automatically)
sudo python3 bin/patch_no_gen1.py apply
```

Expected output:
```
signature hits: original form 1, patched form 0
  located at 0x127da6  (offset 0x127d66 within the .text section)
  lea imm8 @ 0x127da8 = 0xff   (orig 0xff / patched 0xfe)
  cmp imm8 @ 0x127dc3 = 0x02   (orig 0x02 / patched 0x01)
backed up -> .../nvidia.ko.orig_nogen1
written: 8d 42 fe ... 83 f8 01 0f 87
new md5: 514de9d4fdd7c407a088f1baf4b62f04
```

### Step 3 — reload the driver (make the patch take effect)

```bash
# unload cleanly (Xorg / any CUDA process holds /dev/nvidia*)
sudo rmmod nvidia_drm nvidia_modeset nvidia_uvm nvidia 2>/dev/null
lsmod | grep -E '^nvidia' && echo "still loaded; check fuser -v /dev/nvidia* first"

# reload
sudo modprobe nvidia
sudo modprobe nvidia_uvm
```

### Step 4 — unlock the declaration and push

```bash
# load gen2kr (it attaches a kretprobe on nv_pci_probe)
sudo insmod build/gen2kr.ko

# trigger one probe: the push runs the instant probe returns
sudo sh -c 'echo 0000:01:00.0 > /sys/bus/pci/drivers/nvidia/unbind'
sleep 1
sudo sh -c 'echo 0000:01:00.0 > /sys/bus/pci/drivers/nvidia/bind'

# wait and look
sleep 6
lspci -vv -s 01:00.0 | grep -o 'LnkSta:.*'      # expect Speed 5GT/s
sudo python3 bin/peek-regs.py                    # expect LNKSTA CurSpeed=2, CAP2=0x06
sudo dmesg | grep gen2kr | tail -6               # expect "★ SUCCESS Gen2 LNKSTA=1042"
```

### Step 5 — verify

```bash
# A) bandwidth (★ must be 512MB×15)
build/bwtest2 512 15 | grep pinned
#   expect: pinned H2D med ~1.56   D2H med ~1.71  GB/s

# B) stability: run several CUDA contexts back to back; the link must not drop even once
for i in 1 2 3 4 5; do
    build/minictx 1 >/dev/null 2>&1
    sleep 1
    lspci -vv -s 01:00.0 | grep -o 'Speed [0-9.]*GT/s' | head -1
done
#   expect: "Speed 5GT/s" all 5 times

# C) patch independence: remove the guard; the link should still hold (proof the patch really took over)
sudo rmmod gen2kr
for i in 1 2 3; do build/minictx 1 >/dev/null 2>&1; sleep 1; done
sleep 8
lspci -vv -s 01:00.0 | grep -o 'LnkSta:.*'
#   expect: still Speed 5GT/s

# put the guard back (safety net)
sudo insmod build/gen2kr.ko
```

### Step 6 — rollback

```bash
sudo rmmod gen2kr 2>/dev/null
sudo python3 bin/patch_no_gen1.py revert
sudo rmmod nvidia_uvm nvidia_modeset nvidia_drm nvidia 2>/dev/null
sudo modprobe nvidia && sudo modprobe nvidia_uvm
```

## Measurement traps (skip this and you will hit them)

| trap | consequence | correct approach |
|---|---|---|
| using `nvidia-smi` to read the PCIe generation | **it reads a driver cache**; reports 1 even when the registers are already Gen2 | read `LNKSTA[3:0]` only, via `bin/peek-regs.py` |
| `grep 'Speed 5GT/s'` | **false-matches `Speed 2.5GT/s`** (substring) | read registers, or `grep -E 'Speed 5GT/s[^.]'` |
| measuring bandwidth with `128MB×3` | lands inside the link-recovery window; you only measure 0.78 | **must use `512MB×15`** |
| testing "does the patch work" with the guard loaded | untestable — the guard pulls the link back | `rmmod gen2kr` first, then test |
| `perf script` without `-F iregs` | registers can never be read -> treating "didn't see it" as "didn't happen" | must use `perf script -F comm,iregs` |

## Notes and known limitations

### Multi-card machines: the scripts find the card automatically; several identical cards require an explicit target

The scripts no longer hardcode `01:00.0`; they scan `/sys/bus/pci/devices` for `10de:1b87` (P104-100).
Finding **0 cards or more than 1** is a **hard error**; there is no guessing:

```bash
bash drivers/580.178.04/utils/bdf.sh                 # just show what was found
TARGET_BDF=0000:02:00.0 sudo -E bash bin/push.sh     # explicit target
TARGET_IDS="1b87 1c07" sudo -E bash bin/10-check.sh  # search for several device ids at once
```

Early versions hardcoded `01:00.0` and on multi-card machines would read/write a different card (e.g. a P100),
producing the **fake lock-up** of "CAP2=0x0006 but LNKSTA stuck at 1041".

### Situations that lose the patch
Driver upgrade, DKMS rebuild, kernel change -> `nvidia.ko` gets regenerated and the **patch is silently lost** (no error is reported).
Symptom: one day bandwidth suddenly halves back to 0.78.

```bash
# self-check any time
sudo python3 bin/patch_no_gen1.py check
# [patched] -> normal
# [not patched] -> just run apply again; no reboot needed
```

The guard (gen2kr) is the only safety net for this — so **keep it resident**.

### Pascal only
The `SPEED` field encoding is Pascal's (1=5GT/s, 2=2.5GT/s).
Ampere and later use 2=5GT/s; **the encoding differs, the patch does not transfer**.

### Untested paths
- the `mode=2` / `mode=3` branches: this card's driver only ever calls with `mode=1`, so they **cannot be triggered naturally to verify**.
  Static analysis shows the predicate and branches of both paths are byte-for-byte untouched, but "never ran" is "never ran".
  To use this patch on a Gen3 card, verify `mode=3` separately first.

### State lock-up: only a reboot helps
After repeatedly `rmmod`/`modprobe`-ing the driver, or changing registry parameters, the device can end up in:

```
LnkCap MaxSpeed=1  +  CAP2=0x0002  +  TLS=1  +  LNKSTA constant 1
(but 0x8841C and 0x8872C were both written correctly)
```

Measured, it **does not self-heal**: `unbind/bind` ×6, guard retrain ×13, TLS rewrite ×20 (reads back 1 next round),
re-unlocking the declaration ×9 — all failed. **One full reboot, then the very first push succeeded.**

=> seeing this combination means **reboot directly, don't keep trying**, and don't misread it as "the method is wrong".

### Never use user-space mmap writes while the link is in motion
Measured: **bricked the device 2 times out of 2** (C. ZOMBIE, no Xid at all in `dmesg`; only a reboot helped):

| path | scenario | result |
|---|---|---|
| user-space `mmap("/dev/mem")` write | link just downgraded (within 0.5 s) | **2/2 bricked** |
| user-space mmap write | driver not loaded / link quiet / waited ≥5 s | succeeded repeatedly |
| **kernel `writel` (ioremap)** | link just downgraded (≤200 ms) | dozens of runs, tens of minutes, 0 bricks |

=> **BAR0 link-control register writes must go through the kernel path.** User space is for read-only access, or a one-off push while the link is quiet.

## Script structure convention

All scripts under `bin/` follow the same three-part layout so they read top-down:

```bash
#!/bin/bash
# header comment: what this script does, its pitfalls, how to use it

# ============================================================
# 1. variables
# ============================================================
# all collected here, so you can see the script's dependencies at a glance

# ============================================================
# 2. functions
# ============================================================

# each function does one thing; the function name is what it does
do_something() { ... }

# ============================================================
# 3. main
# ============================================================
main() {
    parse_args "$@"
    precheck   || exit 1
    do_something
}

main "$@"
```

When editing scripts, keep this structure. The benefit is direct: **the tunables are visible at the top,
and main shows the execution order**, without scrolling through a long script.

## About `drivers/`

Patches organized by **driver version**, following the `patches/blob-<version>.diff` convention of
[vGPU-Unlock-patcher](https://github.com/VGPU-Community-Drivers/vGPU-Unlock-patcher).

The patches change concrete bytes of a closed-source binary; **offsets are hard-bound to the driver version** — a new version means re-locating,
no reuse. So one directory per version, pinning "offsets + original bytes + verification data" in place.

Currently there is only one version, `580.178.04`, with three patches inside:

| patch | solves | change |
|---|---|---|
| `gen2` | PCIe bandwidth (Gen1 -> Gen2) | `nvidia.ko`, 2 bytes |
| `delay` | fps stuck at ~40fps (gr3d per-batch delay) | `libnvidia-glcore.so`, 1 byte |
| `whitelist` | same as delay, but patched at the kernel source | `nv-kernel.o_binary`, 10 bytes |

The scripts inside each version directory are numbered; run them right there:

```bash
cd drivers/580.178.04
sudo bash 00-whitelist.sh check     # pre-step (optional): restricted-SKU check
sudo bash 01-gen2-patch.sh check    # required: the nvidia.ko patch
sudo bash 02-gen2-push.sh status    # required: module and link state
```

When this card has nothing to do it stays at P0, burning 22 W for nothing. **With an Xorg holding it it drops to P8 (~7.8 W)**,
and sddm's X11 greeter is exactly that Xorg — so just **turn off autologin**, no need to install anything:

```ini
# /etc/sddm.conf.d/*.conf
[Autologin]
Session=
User=
```

With autologin, sddm skips the display server (`grep -c "Display server starting"` = 0);
turned off, it instead spawns a resident Xorg (`-noreset`, parent process is sddm) that stays after login.

⚠ An `Xwayland` inside a Wayland session doesn't count — measured: with it present the card still sits at P0. Indicator: `pgrep -x Xorg`.

The full procedure is in `drivers/580.178.04/README.md`.

`history/` is the Gen2 research material consolidated from `/data/labs/nvidia`, **kept only for preservation and traceability**:

## AI-generated content disclosure (detailed)

### How it was generated

**All content** in this repo was generated with AI assistance; humans provided direction, verification, and corrections:

| category | note |
|---|---|
| scripts (`bin/*.sh`, `bin/*.py`) | AI-written |
| kernel module (`drivers/<version>/kernel/<kernel>/gen2kr.c`) | AI-written |
| binary patch (`bin/patch_no_gen1.py` and the patch itself) | AI did the reverse analysis, located the offsets, designed the change |
| documentation (`docs/*.md`, this README) | AI-written |
| reverse-engineering conclusions (call chain, register semantics, capability bits) | AI derived via perf breakpoints + static disassembly |

**The key decisions came from humans**: e.g. the idea of "don't heal afterwards; make the driver stop changing instead",
and the methodology of "first ask who is writing", were human proposals; AI did the reverse engineering and implementation on top of them.

### "It runs" does not mean "the AI was right"

Along the way the AI **gave wrong conclusions multiple times**, all overturned by later measurements. Three examples:

| the AI's conclusion at the time | later measurement |
|---|---|
| "`SPEED=2` is the endpoint writing it back internally; the CPU can't intercept it; this route is a dead end" | **wrong**. The perf breakpoint simply wasn't firing; SPEED is written entirely by software. This wrong conclusion cost the project an extra day |
| "`rmmod`+`modprobe` resets the declaration back to Gen1" | **inaccurate**. A plain reload does not reset; only a bus reset does |
| "writing the COMMIT bit always bricks" | **mis-attribution**. The driver itself writes COMMIT; what was lethal was missing the prerequisite steps |

All of these are faithfully recorded in `docs/experiment-history.md` and `docs/safety-discipline.md`.
**For any conclusion, verify it yourself before believing it.**

### On patching the NVIDIA driver binary

This must be stated clearly:

- this solution **modifies the machine code of `nvidia.ko`** (a 2-byte immediate),
  changing the driver's internal speed-selection logic
- this is **not** an NVIDIA-sanctioned practice and may violate its license terms
- what the patch **bypasses** is the driver's decision to limit the link per the vBIOS declaration;
  it does not modify signatures, does not crack licensing, does not bypass feature restrictions
- driver upgrades overwrite the patch; re-apply it
- if you use this in a commercial setting, assess compliance yourself

### Boundaries of applicability

| verified | not verified |
|---|---|
| P104-100 (`10de:1b87`) | P106-100 and other Pascal cards |
| Debian 13 / kernel 6.12.113 | other kernel versions (RM offsets may differ) |
| NVRM 580.178.04 | other driver versions |
| the `mode=1` branch (the only one the driver uses) | the `mode=2` / `mode=3` branches |
| x86_64 | other architectures |

Ampere-and-later cards use a **different SPEED encoding** (`2` means 5GT/s); **the patch does not transfer**.
